## Summary

Registered users sign in with email and password so they can access their groups and the rest of the product. Valid credentials establish a Nest-issued JWT session (access + refresh); invalid credentials return a safe, non-enumerating error. Sessions follow ADR-0001 (15m access / 7d refresh; web httpOnly cookies; mobile secure storage) and are cleared on sign-out. Parent epic: [#107 — Authentication & Account Access](https://github.com/chathurka/owezy/issues/107). Builds on E01-S01 registration (`2611071428_register-email-password`) and existing auth scaffolding (JWT guards, BFF refresh/logout stubs, mobile `SessionService`).

## Functional Requirements

- Accept sign-in with email and password on a public endpoint.
- Validate email format and non-empty password client-side and server-side; return actionable field errors for malformed input.
- On valid credentials for an active (non-soft-deleted) user with a password credential, issue access + refresh JWTs (`role` from the user record) and return a minimal user profile.
- On unknown email, wrong password, or soft-deleted account, return the same safe authentication failure (no account enumeration).
- Persist session per ADR-0001: user-web httpOnly cookies via BFF; mobile `flutter_secure_storage` + `SessionService`.
- Clear session on sign-out (revoke client tokens / clear cookies / clear secure storage) so subsequent authenticated requests fail until the user signs in again.
- Optional “Remember me” UI may appear from the Sign in mock; when unchecked, clients still use the standard refresh TTL for MVP (no separate shorter cookie policy until product defines one).
- Google/Apple continue buttons may appear from the Sign in mock but must not call identity providers in this story (E01-S03 / E01-S04).
- Admin console sign-in is out of scope (separate admin auth story / E01-S08 path); this story covers end-user `role: user` sessions on API, user-web, and mobile.

## Acceptance Criteria

- Given a registered active user with correct email and password, when they submit sign-in, then the API returns 200 with access + refresh tokens and user profile (`role`, `emailVerified`, identity fields), and the client establishes a session.
- Given wrong password, unknown email, or soft-deleted account, when they submit sign-in, then the API returns 401 with a stable safe error code (e.g. `INVALID_CREDENTIALS`) and no tokens; response does not reveal whether the email exists.
- Given invalid email format or empty password, when they submit, then the API returns 422 with field-level details and no tokens.
- Given successful sign-in on user-web, when the BFF handles the response, then httpOnly auth cookies are set and the user is navigated into the authenticated `(app)` shell (home/groups entry).
- Given successful sign-in on mobile, when the form succeeds, then tokens are stored in secure storage, `SessionService` becomes authenticated, and navigation leaves the auth stack for the main app.
- Given an authenticated session, when the user signs out, then cookies/secure storage are cleared and protected routes redirect back to sign-in.
- Given social continue buttons on the Sign in screen, when tapped/clicked, then no OAuth call is made in this story (disabled or “coming soon”).
- Given “Forgot password?” link/control, when used, then it may navigate to a stub/route owned by a later story; this story does not implement reset-password APIs.

## Technical Notes

- ADR-0001: Nest JWT access (15m) + refresh (7d); web cookies `owezy_access_token` / `owezy_refresh_token`; mobile `flutter_secure_storage`.
- Password verification with bcrypt against the credential stored at registration; never log passwords or tokens.
- OpenAPI contract: `POST /v1/auth/login` (and reuse existing logout/refresh BFF routes where present).
- Soft-deleted users must not authenticate.
- Unverified email (`emailVerified=false`) still may sign in in this story (same soft gate as register); hard gate deferred to E01-S05 if product tightens later.
- Design: user-web from `resources/owezy-web/00 · Sign in-html/SignIn.dc.html` (+ `pages/SignIn.dc.html`) and screenshots; mobile from `resources/owezy-mobile/prototype/screens/SignIn.dc.html` + DESIGN_SPEC + screenshots.

## Edge Cases & Test Scenarios

- Unknown email → 401 `INVALID_CREDENTIALS` (same as wrong password).
- Wrong password → 401 `INVALID_CREDENTIALS`.
- Soft-deleted account → 401 `INVALID_CREDENTIALS`.
- Malformed email / empty password → 422 with details.
- Empty form submit → client validation; no API call when client-side invalid.
- Network failure on client → actionable error; no partial local session.
- Sign-out while already anonymous → idempotent success (cleared state).
- Concurrent sign-in attempts → each independent; last successful write wins for local session store.

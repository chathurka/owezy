## Summary

Users confirm their email with a valid, unexpired verification code/token issued at registration (or resend). Invalid or expired codes show a recovery path; resend is abuse-protected and does not reveal whether an email is registered. Parent epic: [#107](https://github.com/chathurka/owezy/issues/107). Builds on E01-S01 token rows + Resend adapter.

## Functional Requirements

- Consume a verification token/code: mark `email_verified=true` and consume the token.
- Reject invalid, expired, or already-consumed tokens with a stable error and no side effects.
- Allow authenticated or anonymous resend by email; always return a non-enumerating success.
- Rate-limit resends per email (cooldown) to prevent abuse.
- User-web: `/verify-email` handles `?token=` deep link and recovery/resend UI.
- Mobile: Verify email screen matching mock (code entry + resend countdown).
- Admin excluded.

## Acceptance Criteria

- Given a valid unexpired unconsumed token, when verified, then `email_verified` becomes true, token is consumed, API returns 200 with confirmed user email.
- Given invalid/expired/consumed token, when verified, then API returns 400 `VERIFICATION_TOKEN_INVALID` and recovery guidance is shown on clients.
- Given resend for any email, when requested, then API returns 204; if an unverified active user exists and cooldown elapsed, a new token is emailed.
- Given resend within cooldown, when requested, then API still returns 204 without sending another email.
- Given user-web `/verify-email?token=…`, when opened, then the client attempts verify and shows success or recovery.
- Given mobile Verify email screen, when user enters code and confirms, then session profile reflects verified state.

## Technical Notes

- Reuse `email_verification_tokens`; prefer 6-digit numeric codes (hashed) to match mobile mock; email includes code + web link.
- Cooldown default: 60s (`VERIFICATION_RESEND_COOLDOWN_SECS`).
- OpenAPI: `POST /v1/auth/email/verify`, `POST /v1/auth/email/resend`.
- Design: mobile `VerifyEmail.dc.html`; user-web adapted from SignIn/SignUp auth chrome (no exact verify mock).

## Edge Cases & Test Scenarios

- Already verified user + resend → 204, no email.
- Soft-deleted user + resend → 204, no email.
- Concurrent verify of same token → one success, one invalid.
- Empty token → 422.

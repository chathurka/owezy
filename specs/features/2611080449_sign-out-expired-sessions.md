## Summary

Users can sign out cleanly and see a clear path back to sign-in when a session expires. The API exposes refresh-token exchange so short-lived access tokens can renew; logout clears client credentials and revokes the presented refresh token when possible. Applies to API, user-web, mobile, and admin-web. Parent epic: [#107](https://github.com/chathurka/owezy/issues/107).

## Functional Requirements

- `POST /v1/auth/refresh` exchanges a valid refresh JWT for new access (+ rotated refresh).
- Invalid/expired refresh → 401 `SESSION_EXPIRED` (or `INVALID_REFRESH_TOKEN`).
- Sign-out clears client session (cookies / secure storage) and calls logout; when a refresh token is presented, revoke it server-side.
- Protected routes with expired access attempt refresh once; on failure redirect to sign-in with a clear expired-session message.
- Admin and user webs share the pattern via BFF refresh already stubbed.

## Acceptance Criteria

- Valid refresh → 200 new tokens.
- Expired/invalid refresh → 401; clients clear session and show sign-in with expired message.
- Sign-out → local credentials cleared; subsequent protected calls require login.
- Expired access on protected page → refresh attempt then sign-in path if refresh fails.

## Technical Notes

- Persist refresh token hashes in `refresh_tokens` for revocation on logout/rotation.
- OpenAPI: `POST /v1/auth/refresh`; enhance `POST /v1/auth/logout` to accept optional refreshToken body.
- Design: adapted session-expired messaging on existing Sign in screens (no dedicated mock).

## Edge Cases

- Concurrent refresh → last rotation wins; old refresh becomes invalid.
- Logout without refresh body → still 204; client-cleared.

## Summary

New end users create an Owezy account with email and password so they can start using the product. Registration validates required fields and password rules, creates the account atomically (no half-usable rows on failure), rejects duplicate emails, and initiates email verification as part of the account flow. Parent epic: [#107 — Authentication & Account Access](https://github.com/chathurka/owezy/issues/107). Builds on ADR-0001 (Nest-issued JWT) and existing auth scaffolding in API core, user-web `(auth)` routes, and mobile `SessionService`.

## Functional Requirements

- Accept registration with full name, email, password, default currency, and terms acceptance.
- Validate inputs client-side and server-side; return actionable field errors.
- Enforce password rules: at least 8 characters, one uppercase letter, and one number.
- Create the user record and password credential in a single transaction; on any failure, leave no usable account.
- Reject registration when the email already belongs to an active account (safe conflict response).
- Persist `emailVerified = false` and send a verification email (token/code) after successful create; full verify UX is owned by E01-S05.
- On success, issue access + refresh JWTs (`role: user`) and return a minimal user profile so clients can establish a session and show the check-inbox success state.
- Public register endpoint (no JWT required). Admin registration is out of scope (E01-S08).
- Google/Apple continue buttons may appear in UI from the Sign up mock but must not call identity providers in this story (E01-S03 / E01-S04).

## Acceptance Criteria

- Given valid name, email, password (meets rules), default currency, and accepted terms, when the user submits register, then a user with `role=user` and `emailVerified=false` is created and the client receives access + refresh tokens plus user profile.
- Given an invalid email, missing name (< 2 chars), weak password, missing currency, or unaccepted terms, when the user submits, then the API returns 422 with field-level details and no user row is created.
- Given an email that already exists on an active account, when the user submits, then the API returns 409 and does not create a second account.
- Given a successful registration, when the response is handled, then a verification email send is initiated (failure of send after commit is logged without exposing secrets; account remains created; E01-S05 covers resend).
- Given successful registration on user-web, when the form succeeds, then the BFF sets httpOnly cookies and the UI shows the check-inbox success state matching the Sign up mock.
- Given successful registration on mobile, when the form succeeds, then tokens are stored in secure storage, session is authenticated, and the UI shows a check-inbox success state (stub layout until a dedicated mobile mock exists).
- Given social continue buttons on the Sign up screen, when tapped/clicked, then no OAuth call is made in this story (disabled or “coming soon”).

## Technical Notes

- ADR-0001: Nest JWT access (15m) + refresh (7d); web cookies `owezy_access_token` / `owezy_refresh_token`; mobile `flutter_secure_storage`.
- Password hashing with bcrypt; never log passwords, tokens, or verification secrets.
- Users are not offline-sync entities; server generates UUID. Soft-delete column `deleted_at` still applied for future account closure.
- Email delivery uses configured Resend settings (`RESEND_API_KEY`, `EMAIL_FROM`); verification token TTL from `VERIFICATION_CODE_TTL` (default 900s).
- OpenAPI is the contract: `POST /v1/auth/register`.
- Design: user-web from `resources/owezy-web/00 · Sign up-html/SignUp.dc.html` + `packages/design-system/user`. Mobile has no Sign up mock — adapt Owezy field/button chrome from `resources/owezy-mobile/docs/DESIGN_SPEC.md` + tokens (not raw Material defaults); borrow structure from web Sign up / Sign in where helpful.

## Edge Cases & Test Scenarios

- Duplicate email → 409 `EMAIL_ALREADY_REGISTERED`.
- Weak password / invalid email / short name / missing currency / terms false → 422 with details.
- Concurrent duplicate registrations → unique DB constraint; one succeeds, one 409.
- Email provider failure after user commit → registration still succeeds; verification pending; send failure recorded without PII/secrets in logs.
- Empty form submit → client validation errors; no API call when client-side invalid.
- Network failure on client → actionable error; no partial local session.
- Auth failure (malformed body) → 400/422, not 500.

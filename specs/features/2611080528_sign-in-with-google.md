## Summary

End users sign in (or register) with Google on mobile and user-web so they do not need another password. The API verifies Google ID tokens, links or creates the correct `role: user` identity (never merging accounts without verified email match), and issues Nest JWTs per ADR-0001 / new ADR-0008. Google sign-in is not available in Admin. Parent epic: [#107 — Authentication & Account Access](https://github.com/chathurka/owezy/issues/107). Builds on E01-S01/S02 email auth and E01-S04 Apple OAuth scaffolding (`oauth_identities`).

## Functional Requirements

- Expose a public API that accepts a Google ID token from the client SDK.
- Verify the Google ID token server-side (issuer, audience, expiry, signature via Google JWKS / tokeninfo-compatible verification) before establishing a session.
- Resolve identity by Google `sub` → existing OAuth link → verified email match → create user.
- Never merge identities without verification: only link when Google asserts a verified email that matches an existing active user with no conflicting provider link.
- On success, issue access + refresh JWTs and return the same session profile shape as email/password and Apple login.
- Enable “Continue with Google” on user-web Sign in / Sign up and mobile Sign in / Create account screens; wire to the Google SDK then the API.
- Reject Google sign-in for Admin (no Admin UI; API creates only `role: user` for Google-provisioned accounts).
- Fail closed on invalid/expired/forged/wrong-audience tokens with a stable error code; never log ID tokens.

## Role-Based Access

| Role | Permitted actions |
|------|-------------------|
| admin | None — Google not offered; cannot provision admin via Google |
| user (anonymous) | Start Google Sign-In; call public Google auth endpoint |
| user (authenticated) | Continue using JWT session established by Google flow |

## Acceptance Criteria

- Given a valid Google ID token for a new Google `sub` with verified email, when the client posts it, then the API creates a `role: user` account (nullable password), links `oauth_identities` with `provider: google`, marks email verified, and returns 200 with tokens + profile.
- Given a valid token whose Google `sub` is already linked, when posted, then the API signs in that user (no duplicate user) and returns 200 with tokens.
- Given a valid token with verified email matching an existing active password/Apple user and no prior Google link, when posted, then the API links Google to that user and returns 200 with tokens.
- Given a valid token that would link the same Google `sub` or email to conflicting accounts, when posted, then the API returns a stable conflict error (`ACCOUNT_LINK_CONFLICT`) and no tokens.
- Given an invalid, expired, wrong-audience, or tampered ID token, when posted, then the API returns 401 `INVALID_GOOGLE_TOKEN` and no tokens.
- Given a token with unverified or missing email and unknown `sub`, when posted, then the API returns 422 `GOOGLE_EMAIL_REQUIRED` and no tokens.
- Given user-web Continue with Google, when the user completes Google Identity Services auth, then the BFF exchanges the token, sets httpOnly cookies, and enters the `(app)` shell.
- Given mobile Continue with Google, when the user completes Google Sign-In, then tokens are stored via `SessionService` and navigation leaves the auth stack.
- Given Admin surfaces, when inspecting login UI, then no Google control is present.

## Technical Notes

- New ADR-0008 (Google Sign-In) required: ADR-0001 deferred IdPs; ADR-0007 covered Apple only and left Google requiring its own ADR.
- Reuse `oauth_identities` (provider value `google`); no new table.
- OpenAPI: `POST /v1/auth/google`.
- Clients: Google Identity Services (user-web) / `google_sign_in` (Flutter); never log ID tokens.
- Linking rules mirror Apple (E01-S04) for consistency; conflicts share `ACCOUNT_LINK_CONFLICT`.
- Design: reuse Sign in / Sign up / Create account mocks — Google is a control on those screens, not a separate page.

## Edge Cases & Test Scenarios

- Google returns verified email on every successful auth (typical) → create/link using email when `sub` unknown.
- Soft-deleted user matched by email → treat as unknown; create new user; do not revive deleted user.
- Soft-deleted oauth identity → treat as unlinked; allow re-link to active user.
- Network / JWKS failure during verify → 401 `INVALID_GOOGLE_TOKEN` (fail closed).
- Client cancels Google sheet / popup → no API call; UI remains on auth screen.
- Password-only login for Google-only user (`password_hash` null) → 401 `INVALID_CREDENTIALS` (existing behavior).
- Email already linked to a different Google `sub` → `ACCOUNT_LINK_CONFLICT`.
- Same email already linked to Apple only (no Google) → link Google to that user (multi-provider allowed when email verifies ownership).

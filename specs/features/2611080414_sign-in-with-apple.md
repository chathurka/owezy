## Summary

End users sign in (or register) with Apple on mobile and user-web so they can use their Apple identity. The API verifies Apple identity tokens, links or creates user accounts safely (including private-relay email), and issues Nest JWTs per ADR-0001 / ADR-0007. Apple is not available in Admin. Parent epic: [#107 — Authentication & Account Access](https://github.com/chathurka/owezy/issues/107). Builds on E01-S01/S02 email auth scaffolding.

## Functional Requirements

- Expose a public API that accepts an Apple identity token (and optional user profile fields Apple returns only on first authorization).
- Verify the Apple identity token server-side (issuer, audience, expiry, signature via Apple JWKS) before establishing a session.
- Resolve identity by Apple `sub` → existing OAuth link → email match → create user.
- Support Apple Hide My Email (private relay): store the relay address as the account email when provided; treat Apple-asserted email as verified.
- On success, issue access + refresh JWTs and return the same session profile shape as email/password login.
- Enable “Continue with Apple” on user-web Sign in / Sign up and mobile Sign in / Create account screens; wire to the Apple SDK then the API.
- Reject Apple sign-in for Admin (no Admin UI; API creates only `role: user` for Apple-provisioned accounts).
- Fail closed on invalid/expired/forged tokens with a stable error code; never reveal whether an email exists beyond safe linking outcomes.

## Acceptance Criteria

- Given a valid Apple identity token for a new Apple `sub` with email, when the client posts it, then the API creates a `role: user` account (nullable password), links `oauth_identities`, marks email verified when Apple asserts email, and returns 200 with tokens + profile.
- Given a valid token whose Apple `sub` is already linked, when posted, then the API signs in that user (no duplicate user) and returns 200 with tokens.
- Given a valid token with verified email matching an existing active password user and no prior Apple link, when posted, then the API links Apple to that user and returns 200 with tokens.
- Given a valid token that would link the same Apple `sub` or email to conflicting accounts, when posted, then the API returns a stable conflict error (`ACCOUNT_LINK_CONFLICT`) and no tokens.
- Given an invalid, expired, wrong-audience, or tampered identity token, when posted, then the API returns 401 `INVALID_APPLE_TOKEN` and no tokens.
- Given private-relay email from Apple, when creating/linking, then the relay address is stored and treated as verified; subsequent Apple sign-ins use `sub` linkage even if email is omitted on later authorizations.
- Given user-web Continue with Apple, when the user completes Apple JS auth, then the BFF exchanges the token, sets httpOnly cookies, and enters the `(app)` shell.
- Given mobile Continue with Apple, when the user completes ASAuthorization, then tokens are stored via `SessionService` and navigation leaves the auth stack.
- Given Admin surfaces, when inspecting login UI, then no Apple control is present.

## Technical Notes

- Migration: `oauth_identities` table; `users.password_hash` nullable.
- Clients: Apple JS (user-web) / `sign_in_with_apple` (Flutter); never log identity tokens.
- Google Continue buttons remain disabled placeholders (no Google ADR).
- Design: reuse Sign in / Sign up / Create account mocks — Apple is a control on those screens, not a separate page.

## Edge Cases & Test Scenarios

- Apple returns no email on subsequent auth → resolve solely by `sub` link; if unknown `sub` and no email → 422 `APPLE_EMAIL_REQUIRED` (cannot create account).
- Soft-deleted user matched by email → treat as unknown; create new user or fail link safely (do not revive deleted user via Apple without product rule — do not revive).
- Soft-deleted oauth identity → treat as unlinked; allow re-link to active user.
- Network / JWKS failure during verify → 401 `INVALID_APPLE_TOKEN` (fail closed).
- Client cancels Apple sheet → no API call; UI remains on auth screen.
- Password-only login for social-only user (`password_hash` null) → 401 `INVALID_CREDENTIALS`.

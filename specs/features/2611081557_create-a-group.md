## Summary

Authenticated users create a shared expense group with a name (required setting). The creator becomes an `owner` member. Extends E02-S04 `POST /v1/groups` with client-UUID idempotency so retries do not duplicate groups, plus post-onboarding Create Group UI on user-web and mobile that lands the new group in the groups list.

## Functional Requirements

- Authenticated user can create a group with a client-generated UUID and name.
- Creator is added as `owner` membership; invite code is generated.
- Retrying create with the same client UUID returns the existing group (no duplicate).
- New group appears in the caller's groups list (`GET /v1/groups`).
- User-web and mobile expose Create Group outside onboarding (New group entry).
- Soft deletes remain on `groups` and `group_members`.

## Acceptance Criteria

- `POST /v1/groups` with valid `{ id, name }` → `201` with group + creator `role: owner`.
- Second `POST` with same `id` by same user → `201` of existing group; no second row.
- Empty/whitespace name → `422` `VALIDATION_FAILED`.
- `GET /v1/groups` includes the created group.
- Clients hold a stable client UUID for a submit attempt and show the group in the list after success.
- No Premium gate.

## Technical Notes

- Builds on E02-S04 GroupsModule (`groups`, `group_members`, invite_code).
- Idempotency key = client `id` (UUID PK); if row exists and `created_by` matches caller, return it; if exists and owned by another user → `409` `GROUP_ID_CONFLICT`.
- Required settings for MVP = group name only; currency and other settings deferred (expense / edit-group stories).

## Edge Cases & Test Scenarios

- Concurrent create with same UUID: one wins; second returns existing.
- Soft-deleted group id reuse: treat as conflict or allow recreate — AI: reject with `GROUP_ID_CONFLICT` (do not revive silently).
- Unauthorized → `401`.

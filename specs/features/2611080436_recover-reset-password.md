## Summary

Users regain access by requesting a password reset email and setting a new password with a time-limited, single-use token. Forgot-password responses never reveal whether an email is registered. Successful reset updates the password hash and invalidates outstanding reset tokens. Admin recovery is out of scope (E01-S08 / ops process). Parent epic: [#107](https://github.com/chathurka/owezy/issues/107).

## Functional Requirements

- Public forgot-password endpoint accepts email and always returns success without enumeration.
- If an active user with a password exists, email a reset link/token (hashed at rest, TTL).
- Public reset-password endpoint accepts token + new password; validates password rules; consumes token; updates password_hash.
- Social-only users (null password_hash) may still receive a reset to set a first password.
- Soft-deleted users are ignored (non-enumerating success on forgot).
- Wire Forgot password links on user-web Sign in and mobile Sign in.
- Admin has no public forgot/reset screens in this story.

## Acceptance Criteria

- Forgot with any email → 204; email sent only when active user exists.
- Reset with valid token + strong password → 200; password updated; token consumed.
- Reset with invalid/expired/consumed token → 400 `RESET_TOKEN_INVALID`.
- Weak password → 422 field errors.
- Clients show forgot + reset screens; success returns to sign-in.

## Technical Notes

- Table `password_reset_tokens` (user_id, token_hash, expires_at, consumed_at, soft delete optional — use consumed_at).
- TTL default 30m (`PASSWORD_RESET_TTL_SECS`).
- OpenAPI: `POST /v1/auth/password/forgot`, `POST /v1/auth/password/reset`.
- Design: adapted from SignIn forgot control + auth chrome (no dedicated forgot/reset mocks).

## Edge Cases

- Rapid forgot requests → allow but reuse cooldown optional 60s (AI: apply same cooldown pattern as verify resend).
- Apple-only user sets password via reset → password_hash populated; email/password login works afterward.
